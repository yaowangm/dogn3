# Internationalization Design

This document records the frontend internationalization framework.

## Status

Implemented in the first pass:

- `static/js/i18n.js` detects browser language, exposes `window.dognI18n`,
  translates current UI labels, and observes future DOM updates.
- `static/index.html` loads `i18n.js` before `app.js`.
- `static/js/app.js` uses the i18n access point for static page-title cases.

The current implementation intentionally combines two approaches:

- A small `t(key, values, fallback)` API for future semantic-key migration.
- A constrained DOM translation pass for the existing UI, so current labels
  can be localized without rewriting every render template in one large pass.

## Goals

- Support multiple interface languages.
- Support at least English and Simplified Chinese in the first version.
- Select the language from the browser language settings for now.
- Make it straightforward to add more languages later.
- Translate all current user-interface text in the first implementation pass.
- Keep the JSON API stable for browser UI and future non-browser clients.

## Initial Language Scope

Initial supported languages:

| Language | Code | Notes |
| --- | --- | --- |
| English | `en` | Default and fallback language. |
| Simplified Chinese | `zh` | Used for Chinese browser language variants for now. |

Chinese handling:

- `zh`, `zh-CN`, and `zh-Hans` map to `zh`.
- `zh-TW`, `zh-HK`, and other Chinese variants also map to `zh` for now.
- A future Traditional Chinese translation can be added as `zh-Hant` or
  `zh-TW` if needed.

All other browser languages fall back to `en`.

## Language Selection

The first implementation uses browser language only:

```text
navigator.languages
navigator.language
```

Selection algorithm:

1. Read `navigator.languages` when available, otherwise use
   `navigator.language`.
2. Normalize each browser language tag.
3. Choose the first supported language.
4. Fall back to `en` when no supported language is found.

No manual language switcher is planned for the first version. If a switcher is
added later, it should store the user's explicit choice in local storage or in
the user profile after login, and that explicit choice should override browser
language.

## File Structure

The no-build structure is:

```text
static/js/i18n.js
static/js/app.js
static/index.html
```

`static/index.html` loads `i18n.js` before `app.js`:

```html
<script defer src="/assets/js/i18n.js?..."></script>
<script defer src="/assets/js/app.js?..."></script>
```

Reasons:

- Translation data stays separate from rendering logic.
- Adding a language does not require searching through page-rendering code.
- The project can keep the current no-third-party-JavaScript approach.
- The file can expose a small stable global API used by `app.js`.

## Translation API

Expose a small browser-global object, for example:

```js
window.dognI18n = {
  language,
  t,
  translateElement,
};
```

Primary helper:

```js
t(key, values = {}, fallback = "")
```

Examples:

```js
t("login.title")
t("post.replyTo", { subject })
t(`error.${code}`, {}, fallbackMessage)
```

Requirements:

- Translation keys are stable semantic keys, not English text.
- Missing keys fall back to English.
- Missing English keys fall back to the provided fallback string.
- Interpolation replaces named placeholders only.
- Dynamic interpolated values must still be escaped by existing HTML escaping
  helpers before insertion through `innerHTML`.

The first implementation also includes an exact-text dictionary for current
UI strings and a small set of regex-style pattern replacements for labels that
include dynamic values, such as:

```text
Page 1 / 4
Author: user name
Reply to: subject
```

Example semantic dictionary shape:

```js
const translations = {
  en: {
    "login.title": "Login",
    "login.resetPassword": "Reset password",
    "post.replyTo": "Reply to: {subject}",
  },
  zh: {
    "login.title": "登录",
    "login.resetPassword": "重置密码",
    "post.replyTo": "回复：{subject}",
  },
};
```

## Translation Key Naming

Use dotted semantic keys:

```text
common.save
common.cancel
common.loading
common.notFound
header.login
header.profile
login.title
auth.error.invalidCredentials
post.meta.author
post.action.reply
user.role.admin
siteManager.category.add
```

Guidelines:

- Use `common.*` for shared buttons, statuses, labels, and units.
- Use page or feature prefixes for specific wording.
- Prefer stable meaning over current English phrasing.
- Avoid using database enum names directly as display text.
- Keep translation keys ASCII.

## Scope Of First Translation Pass

The first implementation translates current visible UI text in:

- Shared header and footer.
- Portal/default page.
- Board page.
- Post detail page.
- Post list page.
- Post print page.
- Post editor page.
- Login page.
- Password reset request and confirmation pages.
- User profile page.
- User list page.
- User add page.
- Site manager page.
- Common errors, empty states, loading states, buttons, labels, tooltips, and
  metadata labels.

User-generated or database content must not be translated:

- Post subjects and content.
- User names.
- Board names and comments.
- Category names.
- Signature text.
- Point-log names.
- Any other data loaded from PostgreSQL.

The DOM translator therefore skips known content containers such as post
titles, post bodies, signatures, and profile text. Future render code should
prefer explicit semantic keys instead of relying on exact-text DOM translation.

## Backend/API Message Strategy

The first implementation should not localize backend JSON messages. Backend
responses should continue to include stable error codes and English fallback
messages.

Frontend behavior:

1. Prefer translating by error code when a known code exists.
2. Fall back to the backend `message` when no translation key exists.

Example:

```js
t(`error.${error.code}`, {}, error.message)
```

This keeps APIs stable for future clients. Backend `Accept-Language` support
can be added later if non-browser clients need localized server responses.

## HTML Escaping And Security

Internationalization must not weaken existing XSS protections.

Rules:

- Translation strings are trusted application resources.
- User-generated and database-loaded values interpolated into translations are
  not trusted.
- Continue using `escapeHtml` for dynamic text inserted through `innerHTML`.
- Prefer text assignment when practical.
- Do not let translation strings contain arbitrary HTML in the first version.
- If rich translated text is needed later, support a small explicit component
  API rather than raw translated HTML.

## Plurals And Counts

The first version can use simple labels where possible because many existing
labels are compact, such as `posts`, `points`, and `views`.

For future plural rules, add a helper such as:

```js
tn(key, count, values = {})
```

Do not introduce plural complexity until a page needs grammatically different
forms.

## Date, Time, And Number Formatting

The first implementation should keep existing backend date strings unless a
specific page already formats them in JavaScript.

Future enhancement:

- Use `Intl.DateTimeFormat` for locale-aware date/time display.
- Use `Intl.NumberFormat` for large counts.
- Keep API values raw enough that frontend clients can format them.

## Implementation Plan

Completed:

1. Added `static/js/i18n.js` with language detection, dictionaries, fallback,
   DOM translation, mutation observation, and interpolation.
2. Loaded `i18n.js` before `app.js` from `static/index.html` and bumped asset
   versions.
3. Added an `i18n` access point in `app.js`.
4. Translated current UI text into Simplified Chinese with English fallback.
5. Kept database content unchanged by skipping known content containers.

Future cleanup:

- Gradually replace exact-text DOM translation with semantic keys in render
  templates when pages are edited.
- Add focused browser tests if frontend test infrastructure is introduced.

## Testing Strategy

Required checks after implementation:

- `node --check static/js/i18n.js`
- `node --check static/js/app.js`
- `cargo check`
- `./scripts/test.sh`

Manual browser checks:

- Browser language English shows English labels.
- Browser language Chinese shows Simplified Chinese labels.
- Unknown browser language falls back to English.
- Login and reset-password errors use localized frontend text where a known
  error code exists.
- Pages still escape user-generated/database text.
